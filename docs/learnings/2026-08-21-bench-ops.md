# Bench Ops Learnings - 2026-08-21 (M1 selftest bring-up)

Operational gotchas discovered while flashing, capturing boot logs, and
verifying the web UI on the bench. Project-level notes; keep new bench
gotchas here.

## 1. Serial reset control (DTR/RTS) - HOST-SPECIFIC

The ESP32 auto-reset circuit is controlled over the USB-serial DTR/RTS
lines. **These procedures were verified on the original Linux bench host
(CP210x on /dev/ttyUSB0); they do NOT transfer verbatim to the Mac host
(#189, 2026-10-11): the documented DTR=1/RTS=0 pulse did not reset the
board there. Verify polarity per host+board before relying on scripted
resets; the EN-button procedure below is the portable one.**

| Sequence | Effect (Linux bench host) |
|----------|--------------------------|
| DTR=1, RTS=0 | Reset pulse (enters download/boot) |
| DTR=0, RTS=0 | Normal boot |
| RTS left =1 at end | Chip held in ROM bootloader - board goes SILENT |

Rule: after any manual DTR/RTS manipulation, always end with DTR=0/RTS=0 and
verify the boot banner appears. A "dead" board after scripting is usually
RTS stuck high, not bricked hardware.

**Reliable reset on any host (verified 2026-10-11)**: open the port with
BOTH DTR and RTS asserted (pyserial: `s.dtr = True; s.rts = True` - safe,
no EN/IO0 pull), start a background reader, then press the EN button on
the board. Expect the `rst:0x1 (POWERON_RESET)` banner within a second.
On the devkit boards the two buttons by the USB plug are EN (reset) and
BOOT (IO0) - a short BOOT tap while running does nothing.

## 2. pyserial location - HOST-SPECIFIC

Default `python3` may have NO `serial` module. Probe per host instead of
hardcoding a venv path:

```bash
python3 -c "import serial" 2>/dev/null && echo system python ok
# Linux bench host:
~/.local/share/pipx/venvs/platformio/bin/python   # pyserial 3.5, always works
# Mac bench host (2026-10-11):
/Users/mw/.local/pipx/venvs/platformio/bin/python  # note: ~/.local/pipx, not share/
uv run --with pyserial script.py                  # on the fly, any host
```

The device name differs too: `/dev/ttyUSB0` (Linux) vs
`/dev/cu.usbserial-0001` (Mac, CP2102). List with `pio device list`.

The boot-capture script lives at /tmp/capture_boot_t011.py (recreate if /tmp
was cleared: open /dev/ttyUSB0 @115200, print timestamped lines until `Idle`).

## 3. Firmware JSON must be parser-verified on target

The /api/status root-object closing-brace bug (`]}}` vs `]}`) passed
`pio test`, `pio run`, and visual inspection, and was only caught by piping
the live endpoint through `jq` on the bench.

Rule: for any JSON endpoint change, verify with
`curl -s http://192.168.4.1/api/status | jq .` after flashing - never
"looks right in the browser".

## 4. BOOT log git hash semantics

`BOOT fw=... git=<hash>` prints the last COMMITTED state at build time. An
uncommitted build reports the previous commit's hash. Do not use the boot
banner to identify uncommitted firmware; check `git status` + build time.
